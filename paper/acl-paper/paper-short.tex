\begin{abstract}
Multilingual agentic benchmarks remain rare, especially for under-resourced languages such as Thai, where
nicknames, unspaced script, and fused honorifics change how an agent must query its tools. We present
\textbf{FahMai-TeleBench}, a bilingual (Thai/English) benchmark for grounded tool use. A model answers
employee-directory questions over a synthetic company directory by issuing tool calls, or refuses when
the answer is absent. All 626 items are synthetic but modeled on a real Thai enterprise-directory
deployment, and they are graded deterministically without an LLM judge. Our central design choice is to
treat \textbf{tool availability as an experimental variable}: each item runs under four tool
configurations (grep, structured search, both, and a Python REPL), so the benchmark measures not just
\emph{whether} a model answers but \emph{how} it uses tools. The task is near-solved at the frontier
(GPT-5.4 97--99\%), yet sharply discriminating for the Thai-capable models an organization would host
itself (Typhoon-2.5 58--74\%, Typhoon-S-8B 25--37\%). The Thai penalty is model-specific, and Typhoon-2.5 answers
90\% of items correctly once the relevant records are placed in its context, so its failures are
failures of tool use. The tool axis also exposes differences at the frontier: GPT-5.5 drops to 73\% with
a wide-schema structured search tool while scoring 97--98\% with grep and the REPL.
\end{abstract}

\section{Introduction}

Most tool-use and function-calling benchmarks are English
\citep{patil2023gorilla,qin2023toolllm,yao2024taubench}, so we know little about how agents behave when
the language itself complicates the task. Thai is a useful stress test. People are addressed by
nicknames that bear no systematic relation to their formal names, the same given name recurs across
many employees, and romanizations are idiosyncratic. Because Thai is written without word spaces, an
honorific title fuses with the name it precedes (คุณกมลา, ``Khun Kamala''), so a literal search for
the user's string returns nothing. These properties change how a model must query a tool, not merely how
it reads text. We study a common enterprise setting in which they all appear at once: an
employee-directory assistant.

The task is deliberately simple. A user asks for a colleague's phone extension, email, or department
head, and the model answers by calling a tool over a company directory, or refuses when the directory
does not contain the answer. We do not design the benchmark to defeat the strongest models; instead, we
measure how existing models use combinations of common tools. This simplicity has two payoffs. First, each item
has a unique gold answer computed from the directory, so grading is a deterministic string check with no
LLM judge, and frontier models solving nearly every item confirms that the golds are reachable. Second,
an easy task that the frontier solves still spreads models apart below it, in the \emph{deployable
tier}: open-weight models that an organization can host itself, keeping personnel records in-house, and
can afford to run at assistant volume. There the spread is large: a Thai-specialized 8B model (Typhoon-S-8B) scores 25--37\%, while
larger open-weight models exceed 95\%.

We run every item under four tool configurations: a raw-text grep, a structured search with 14 optional
filter fields, both together, and a Python REPL. Holding the item fixed and varying only the toolset
exposes process-level behavior that a single accuracy number erases, such as retry after a failed query
and tool routing when alternatives compete. On a hard benchmark, ``chose the wrong tool'' is
indistinguishable from ``task too hard''; on an easy and well-posed one, the mechanism becomes legible.

The benchmark therefore separates two axes. The \emph{language axis} compares Thai and English items
within the same subtype, and the \emph{tool axis} compares identical items across toolsets. This lets us
ask whether multilingual ability, as measured by text-only evaluation, carries over to agentic use. For
Typhoon-2.5, the Thai model we test in depth, it does not. When the relevant directory records are
placed in its prompt, it answers 90\% of a 149-item sample correctly. When it must find the same records
with tools, it answers only 48--71\% of those items.

We make four contributions. First, we release
\textbf{FahMai-TeleBench}\footnote{Code (MIT) and data (CC BY 4.0): \url{https://github.com/yongsa-nut/FahMaiTeleBench}.}, a
626-item bilingual benchmark for grounded directory tool use, with deterministic grading and gold answers
checked by human raters. Second, we design a question taxonomy that covers Thai-specific retrieval
phenomena and spans both \emph{depth} (multi-hop org bridges) and \emph{breadth} (listing and
aggregation), with a five-way refusal taxonomy. Third, we propose a tool-availability design, with four
tool configurations per item, that measures the tool-use \emph{process} rather than only the outcome.
Finally, we evaluate twelve model variants and show that accuracy separates models mainly below the
frontier, that the tool axis exposes differences at the frontier, and, with a per-language analysis and
an oracle-context control, that the Thai-specialized models' failures are failures of tool use rather
than of reading Thai.

\section{Related Work}

\paragraph{Tool-use benchmarks.} Early work targets API and function calling: Gorilla
\citep{patil2023gorilla} and the Berkeley Function-Calling Leaderboard \citep{patil2025bfcl}, ToolLLM over
16{,}000+ REST APIs \citep{qin2023toolllm}, and API-Bank \citep{li2023apibank}. Later benchmarks add
interaction and multi-hop structure: $\tau$-bench and $\tau^2$-bench emulate user--agent conversations
under domain policies \citep{yao2024taubench,barres2025tau2bench}, ToolSandbox adds stateful
conversational tool use \citep{lu2024toolsandbox}, and ToolHop targets multi-hop tool chaining
\citep{ye2025toolhop}. Recent suites scale to 220 tools on real Model Context Protocol servers
\citep{bandi2026mcpatlas} and grade autonomous-agent trajectories across nine task categories
\citep{ye2026claweval}, and broader environments include AgentBench \citep{liu2023agentbench}, WebArena
\citep{zhou2023webarena}, and AppWorld \citep{trivedi2024appworld}. These benchmarks are almost all
English and typically hold the toolset fixed. We make the toolset an experimental variable, and we
target Thai.

\paragraph{Grounded querying and refusal.} Text-to-SQL benchmarks such as Spider \citep{yu2018spider} and
BIRD \citep{li2023bird} grade an executed query against a gold result, but their queries are typically
single-shot. Knowing when \emph{not} to answer has been studied notably in SQuAD~2.0
\citep{rajpurkar2018squad}, and tool-use safety in ToolEmu \citep{ruan2023toolemu}. We keep exact,
reference-based grading inside an agentic, multi-tool loop, and we add a five-way refusal taxonomy.

\paragraph{Thai and Southeast Asian evaluation.} Evaluation for Thai and Southeast Asian languages has
centered on language understanding and knowledge. Typhoon introduced a family of Thai LLMs and the
ThaiExam benchmark \citep{pipatanakul2023typhoon}, and SEA-HELM provides a holistic suite across SEA
languages \citep{susanto2025seahelm}; related efforts include SeaLLMs \citep{nguyen2023seallms} and the
SEACrowd data hub \citep{lovenia2024seacrowd}. None of these target grounded agentic tool use, which for
Thai remains largely unmeasured.

\section{FahMai-TeleBench}

\paragraph{Data.} The knowledge base is the telephone directory of one fictional company, \textbf{FahMai
Co.} (ฟ้าใหม่), with \textbf{1{,}995 employee records} across 19 fields: Thai and romanized names,
nicknames, extensions, emails, titles, and an org hierarchy of unit $\subset$ section $\subset$ department
(16 departments, five of them house brands) over 11 branches. The schema and the query types follow a
real Thai enterprise-directory deployment. Each first name and nickname is drawn at random from public
Thai name lists, skewed toward uncommon names, and each surname is compounded from common Thai surname
parts. No record is copied from a real person. Every record and item is newly generated, so no model
trained before the release can have seen them. Every item has a unique gold, whether a single row, a complete set, or an exact count: given
names and nicknames are deliberately shared across employees, but each item's constraints jointly
identify one answer (in two items, either of two employees). Some fields are deliberately blank, as in real directories where many employees
record no nickname; these support the field-blank refusals. We fix one schema on purpose: holding the
knowledge base constant is what makes the tool configuration the only varied factor. The released
generator can produce organizations with other schemas, sizes, and blank profiles.

\paragraph{Construction.} Deterministic scripts generate the directory and the items. A seed-pinned
generator fills an org chart, with headcounts per department and position level, with generated
employees; it keeps 95--98\% of surnames unique apart from planted family clusters, shares nicknames to
create homonyms, and leaves fields blank at controlled rates. Thirteen scripts build the items: a random
generator (261 items, 21 subtypes) and twelve targeted scripts covering one to four subtypes each.
(i)~A script selects rows that fit the subtype, e.g., an employee whose given name 12 others share but
whose title is unique. (ii)~It phrases the question: 388 items fill one of 159 Thai or English templates, 161 use a question written for the item, and 77 are individually edited versions of either. (iii)~It reads the gold from the selected rows: a field value, the full member set, or a
computed count. The checks are queries over the directory, not keyword matches on the question: they
count the rows that meet an item's constraints, compare a superlative's top value with the runner-up, or
search every name field for a not-found name. A separate checker then re-derived each item's constraints
from its question text, evaluated them on the directory, and graded an ideal answer for every matching
row (Appendix~\ref{app:construction}, Table~\ref{tab:construction}). Phrasing follows a style guide drawn
from real usage logs: questions read as a user would type them and never gloss a directory code, a field
name, or the answer's role. An LLM coding assistant wrote the scripts, including every template and written question, from our taxonomy and style guide; every gold is
computed from directory rows, not stated by a model, and we reviewed the items manually.

\paragraph{Validation.} Two native Thai raters, one of them an author, independently checked a stratified 10\% sample (58 items, all 29 subtypes) against the
directory rows that define each gold. Raw agreement on gold correctness, well-formedness, and
naturalness is 91\%, 97\%, and 95\% (Gwet's AC1 0.91, 0.96, and 0.95). Every instance of the issue types the
raters found has been corrected across all 626 items (Appendix~\ref{app:human}).

\paragraph{Question types.} The 626 items span eight groups and 29 subtypes (Appendix~\ref{app:tax}): A
identity lookup, B name resolution, C counting and aggregation, D disambiguation, E multi-hop, F org and
brand knowledge, G bilingual and code-switched fields, and H refusal. Items are 38\% English and 62\%
Thai; 521 require an answer and 105 a refusal. Several subtypes target the Thai phenomena above. Noisy-name
resolution (B2, B3) requires normalizing a nickname or honorific-wrapped name; B3's hard tier (10 of its
20 items) gives only a shared given name and a company-unique role, forcing disambiguation among 9--13
homonyms. Multi-hop bridges (E1, E2, E4) compose chains of up to four hops through org-unit nesting and a
secretary$\leftrightarrow$executive bridge, since the directory has no manager field. Listing and
aggregation items (group C, multi-entity turns D3, and implicit-hierarchy listings E3) require a complete
set rather than a single row, and premise correction
(F2) requires rejecting a false premise. The refusal group (H) covers five reasons: field not in the
table, person not found, subjective question, out-of-company entity, and blank field.

\paragraph{Tools and grading.} We expose three tool types and run every item under four tool
configurations (Table~\ref{tab:tools}). Because only the toolset changes across configurations,
differences in accuracy or behavior are attributable to tool affordance, not the item. Answer items pass
if the response contains every required gold entity (in Thai or romanized form) and, for counts, the gold
number as a standalone number. Refusal items pass if the response contains one of the accepted phrasings
for their reason (a canonical Thai phrase and close Thai or English paraphrases) and leaks no extension or
employee ID. Every verdict is a deterministic string operation, so grading is exactly reproducible from
the released model outputs.

We evaluate \textbf{twelve model variants} (eleven models; GPT-5.5 at two reasoning efforts) in three
tiers. The \textbf{closed-source} tier comprises GPT-5.4 (medium), GPT-5.5 (medium and low), Claude
Sonnet~4.6 (non-thinking), and Gemini-3-Flash. The \textbf{open-weight} tier comprises GLM-5.1,
DeepSeek-V4-Pro, DeepSeek-V4-Flash, Gemma-4-31B, and MiniMax-M2.7. The \textbf{Thai open-weight} tier
comprises Typhoon-2.5 (30B) and Typhoon-S-8B, the latter from Thailand's national ThaiLLM
initiative\footnote{The other 8B models released under the ThaiLLM initiative do not produce tool calls,
so a tool-use benchmark cannot evaluate them.}, post-trained on a Qwen3-8B-based backbone \citep{qwen3,pipatanakul2026typhoons} and
served with a 16k-token context window. We call each model through its provider's tool-calling API,
directly or through OpenRouter, with a shared system prompt; evaluation runs took place between May and
September 2026, and the DeepSeek models were run on the April 2026 V4 weights, through DeepSeek's API and
through fp8 hosts on OpenRouter. We set the temperature to 0 where the
provider supports it (0.2 for the two Typhoon models); reasoning models use their default sampling. An
agentic loop is capped at \textbf{seven tool-call rounds}, and round-exhaustion counts as a failure. We
retry transient provider errors (HTTP 5xx or empty responses), so the failures we count are wrong answers,
round-exhaustion, context-window overflow on the largest tool results, and malformed tool calls. Following SEA-HELM's reported
results \citep{susanto2025seahelm}, we run a single pass per cell; we report 95\% percentile intervals
from a nonparametric bootstrap over items (2{,}000 resamples), which capture item-sampling uncertainty but
not run-to-run variation.

\section{Results}
\label{sec:results}


\paragraph{Near-solved at the frontier, discriminating below it.} Seven of the twelve model variants (six
distinct models) reach 95\% or more on their best tool configuration (Table~\ref{tab:leaderboard}), which
shows that the items are answerable as specified. Below this group the spread is wide and ordered:
Gemini-3-Flash, Gemma-4-31B, and MiniMax-M2.7 reach 81--93\% across configurations, Typhoon-2.5 58--74\%,
and Typhoon-S-8B 25--37\%. The two Thai-specialized models trail all others by far more than the bootstrap
half-widths (at most about four points); the other gaps are smaller. Open weights are not the bottleneck:
GLM-5.1 and DeepSeek-V4-Flash reach 97.8\% and 97.4\% on their best configuration, on par with the closed
frontier. Accuracy therefore separates models mainly in the smaller and Thai-specialized part of the
deployable tier; at the frontier, the tool axis separates them.

\paragraph{Tool availability is the variable.} Holding the item fixed and varying only the toolset moves
scores substantially, and the direction differs by model. The clearest case is Sonnet~4.6 on noisy names (B3,
$n=20$): 90\% with grep alone and 50\% with structured search alone, because substring grep tolerates
the noise and exact-field filters do not. Offered both, Sonnet~4.6 opens with search on 167 of the 169 items in the
subtypes where grep is the better tool, and reaches 70\% on B3. Retry behavior, read off the grep-only traces, also separates models. On the 90 name- and
shorthand-resolution items (nickname variants B2, noisy names B3, enterprise shorthand B4, and brand and
branch priors F1), GPT-5.4 issues a second, different query on 49 and solves
95\% of B3, whereas Typhoon-2.5 never does (0 of 90) and solves no B3 item. None of this is visible in a
single-tool, outcome-only score.

\paragraph{A tool-schema sensitivity: GPT-5.5's search-tool loop.} GPT-5.5 is frontier-class with grep
(96.8/96.3\%, medium/low effort) and the REPL (97.6/98.1\%) but drops to 73.0\% and 65.5\% with the
structured search tool. The mechanism is a degenerate loop: it fills the search tool's optional fields
with hallucinated values, gets empty results, and repeats the call until the seven-round cap. Of
GPT-5.5-medium's 169 search-tool failures, 152 (90\%) are round-exhaustion, against two exhaustions in all
its other configurations combined, and no other model exceeds 18 round-exhaustions across all
configurations (Table~\ref{tab:failmodes}). Offering grep alongside (T3) lets GPT-5.5 route around the
search tool and largely recover (95.7\%). Both efforts fail by looping on the same number of search items (152 each),
but these sets overlap only partly (Jaccard similarity 0.25), which suggests that the loop is a property of the model--interface pairing rather
than of particular items. The drop is language-independent (Table~\ref{tab:lang}).

\paragraph{Language axis versus tool axis.} Because the English and Thai halves are not parallel
translations, we compare the two languages within subtypes (Table~\ref{tab:lang}). The Thai penalty is
model-specific rather than uniform. GPT-5.4, GPT-5.5, GLM-5.1, and both DeepSeek models show little or no
Thai penalty ($\Delta$ between $-1.6$ and $+0.2$), while Gemma-4-31B, Gemini-3-Flash, Sonnet~4.6, and
MiniMax-M2.7 pay about four to seven points. The Thai-specialized Typhoon-2.5 shows the reverse pattern and scores higher on Thai.
Language can also shift behavior rather than accuracy: nearly all of Sonnet~4.6's failures on bilingual field
lookups are Thai-phrased employee-ID requests that it refuses as personal data. The tool axis, in
contrast, moves every model regardless of language, and it explains most of Typhoon-2.5's deficit. On the
refusal group, which demands Thai comprehension and a phrasing contract but little tool work, Typhoon-2.5
scores 95.5\%, against 59.5\% on the tool-requiring remainder. An oracle-context control makes the
comparison direct (Appendix~\ref{app:oracle}): with tools disabled and the gold rows placed among
distractors in the prompt, Typhoon-2.5 answers 89.9\% of 149 answer items, against 48.3--71.1\%
agentically on the same items, while Gemma-4-31B stays within its agentic range (91.3\% against
86.6--91.3\%). Typhoon-2.5 reads the Thai records well; operating the tools is what it cannot reliably do,
and a text-only multilingual evaluation would miss this.

\paragraph{Error analysis.} Every one of the 626 items is solved by at least one model variant, a
necessary (though not sufficient) condition for gold validity, and only one item is failed by GPT-5.4
under all four configurations. Failure types differ by model (Appendix~\ref{app:errors}): GPT-5.4's
failures are all wrong answers, more than half of GPT-5.5's are round-exhaustions from the search loop, and
Gemma-4-31B's are almost all wrong answers.

\section{Discussion and Conclusion}

An easy task examined carefully can be more informative than a hard task examined coarsely. The frontier
is near its ceiling by design: on a simple but real task, the small local models one may actually deploy
still struggle, and the reason is tool use rather than language. Two practical implications follow from
the tool axis. First, the tool \emph{interface} can matter as much as the choice of model: GPT-5.5
(medium) swings 24 points between grep and search, and Sonnet~4.6 loses 40 points on noisy names when grep is
replaced by search, and 20 when it must choose between them. Second, offering both a structured and a
raw-text tool is cheap insurance: for eight of the twelve variants, T3 is within one point of the best
configuration, and it is never more than 4.3 points below it.
The GPT-5.5 result further suggests that easy, well-posed benchmarks can serve as regression detectors. Finally, a model's multilingual ability measured on text
does not predict its agentic behavior in that language, which argues for evaluating agents in the
languages they will serve.

\section*{Limitations}

We deliberately fix one schema and one domain, so that the tool configuration is the only factor that
varies; results may not transfer to directories with other schemas (for example, with explicit manager
fields) or to other domains. Gold validity rests on checks at construction, on an automated re-check of
every item against the directory, on every item being solved by at least one model, and on a two-rater
validation of a 58-item stratified sample; the remaining items were reviewed by the authors but not
independently validated. The question phrasings were written by an LLM coding assistant; they follow a
style guide drawn from real usage logs but may still differ from how real users phrase requests. Grading is string-based: golds list
Thai and romanized forms and refusals accept a fixed set of paraphrases, so a correct answer in an
unanticipated surface form is scored wrong. Each cell comes from a single run. The bootstrap intervals
reflect which items were sampled, not how much a score would change if the same items were run again;
that change may be larger for the reasoning models, which ran at their default sampling temperature
rather than at 0. Open-weight models were queried
through third-party providers whose serving precision we do not control, and Typhoon-S-8B's 16k-token
context limits how much tool output it can read. The seven-round cap bounds the deepest items, and
genuinely interactive refinement, such as clarification turns, is out of scope. Finally, difficulty is
calibrated to current models and will likely erode as they improve, though the GPT-5.5 result suggests
this erosion need not be monotonic.

\label{app:construction}

\paragraph{Re-check against the directory.} A separate checker tests whether each question determines its
answer. For each item it re-derives the constraints stated in the final question text and evaluates them
on the directory. In 427 items the constraint values are parsed with the template that generated the
item and matched by exact field equality; in 193, one phrase is first mapped to a field value by a
recorded annotation (for example, ``VP of Logistics'' to the position VICE PRESIDENT LOGISTICS, or a fixed
list of the fruit and colour words among the 188 distinct nicknames). For every row that satisfies the
constraints, the checker grades an ideal answer with the benchmark's grader. An item that fails is corrected:
a question that more than one employee satisfies names the target's level or rank, or its gold accepts
both readings (16 items); a count must equal the directory's (2 items); and a listing's gold credits every
valid member and requires nothing the question does not ask for (46 items). Of the 626 items, 469
single-answer and refusal items match exactly one row or have a refusal reason
that holds, and 148 count, set, or two-reading items have golds consistent with the directory. Three
items identify a department's head by its unit code (the department code plus VP), since that department
has three VPs, and six depend on facts outside the directory's fields: three reporting-line items, which
we checked against the organization chart behind the directory, and three regional-geography items. The
checker flagged all eleven items in a deliberately corrupted control set.

\paragraph{Worked example.} One hard-tier item of subtype B3 asks ``What's the extension for Thavan, the
GM of Saifah?'' Its build script makes it in the three steps of Section~3.

\paragraph{(i) Selection.} The target is Thawan Boonnamphong, General Manager of the Saifah brand.
Thirteen employees share the given name Thawan (ถาวร), but no one else holds this title, so the title alone
identifies the target.

\paragraph{(ii) Question.} The question spells the name ``Thavan'', a w$\to$v romanization variant that
matches no name field in the directory. A literal search for the user's string returns nothing, so the
model must normalize the name, and only then can the title narrow the 13 candidates to one.

\paragraph{(iii) Gold.} The gold is the extension on the target's row (79517). The extensions of the other
twelve Thawans are forbidden, so a response that names the wrong Thawan fails even if it also contains
79517.

\paragraph{Checks.} Before writing the item, the script confirms that ``Thavan'' has no hits in the four
name fields, that exactly one employee holds the title, and that the gold differs from every forbidden
value. If any check fails, the script aborts. Items from the random generator follow the same steps, except that step (i) samples rows at
random from those that meet the subtype's condition and step (ii) draws one of several templates; for a
reverse lookup (A3), for instance, it fills ``ext \{ext\} belongs to?'' or ``ต่อ \{ext\} เบอร์ใคร'' with a
sampled extension, and the gold is that row's first and last name.

\section{Failure Types}
\label{app:errors}

We bucket each failure from its trace and sum over the four tool configurations

retries, mostly a context-window overflow on a large tool result and in four cases malformed tool-call
arguments. For each
subtype, taking the mean over the twelve model variants of each variant's best configuration, the hardest
subtypes are the multi-hop bridges (E1 76\%, E4 83\%), noisy-name resolution (B3 83\%), brand unit heads

\section{Human Validation of the Gold Answers}
\label{app:human}

\paragraph{Sample.} The 58-item sample stratifies 10\% of each of the 29 subtypes and includes the single
item that GPT-5.4 fails under every configuration. Both raters labeled the same items.

\paragraph{Protocol.} Each rating page shows the question, the evidence that defines the gold, and the
expected answer; it never shows model outputs or grader verdicts. The evidence is the ground-truth
directory row or rows, tailored to each refusal reason: the full schema for field-not-in-table items,
near-miss rows and a whole-table scan for person-not-found items, and the person's row with the blank
field highlighted for field-blank items. Superlative items show the computed ranking, and multi-hop items
show the bridge person's row and the section roster. The rater answers three questions: does the gold
match the evidence, is the question well-formed, and does it read naturally.

\paragraph{Agreement.} Raw agreement is 91\% (gold correctness), 97\% (well-formedness), and 95\%
(naturalness), and Gwet's AC1 is 0.91, 0.96, and 0.95. We report AC1 because both raters answer ``yes''
on more than 90\% of items, a prevalence regime in which Krippendorff's $\alpha$ is degenerate. Both
raters confirmed the gold on 53 of the 58 items. Checking the other five against the directory found one
wrong gold, which omitted the extension its question asked for; the other four golds were correct.

\paragraph{Full-set check.} The raters' flags point to two issue types that can recur across items: a
gold that does not accept the phone number its question asks for, and a question that glosses a
directory code in parentheses. A check of all 626 items for both, and for golds whose token also appears
in the question, ensures that every gold accepts the number its question asks for, no gold can be
satisfied by a token from its own question, and no question glosses a code, a field name, or the answer's
role; 73 items needed a correction. With the re-check in Appendix~\ref{app:construction}, 14 of the 58
sampled items differ from the versions the raters labeled (11 in wording, 3 in gold); the agreement
figures describe the labeled versions.

\section{Oracle-Context Control}
\label{app:oracle}

do not contain the chain. For each item, the prompt contains the question and a 12-row CSV excerpt: the
